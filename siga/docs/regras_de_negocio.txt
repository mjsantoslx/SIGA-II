1. Princípio fundamental

A partir deste momento:

Nenhuma decisão funcional já fechada pode ser alterada ou esquecida numa nova versão sem uma decisão explícita.

Antes de gerar qualquer versão futura, a implementação deverá ser confrontada com esta especificação.

2. Base de dados
2.1 Motor de base de dados

O projecto continua em:

MySQL / MariaDB

A eventual migração para:

PostgreSQL;
Microsoft SQL Server;

foi considerada, mas não faz parte do desenvolvimento actual.

2.2 Charset e collation

A escolha definida é:

utf8mb4
utf8mb4_uca1400_as_ci

2.3 Instalação limpa

Devido às alterações estruturais profundas da V14:

a instalação parte de uma base de dados nova;
existe um único script de criação;
não devem existir scripts de migração intermédios no pacote de instalação.

O pacote deve conter:

Código da aplicação
+
Script único de criação da BD
+
Dados iniciais
3. Modelo pessoas

Foi adoptado o conceito de Pessoa como entidade base.

Os dados pessoais que podem ser comuns a diferentes entidades devem estar centralizados em:

pessoas

O associado deixa, portanto, de concentrar directamente todos os dados pessoais.

A relação é conceptualmente:

pessoas
   │
   └── associados
4. Associados

A tabela de associados deve conter os dados específicos da condição de associado.

4.1 Dados pessoais relevantes

Foram definidos, entre outros:

nome;
nome do pai;
nome da mãe;
género;
nacionalidade;
estado civil;
confissão religiosa;
tipo de documento de identificação;
número do documento;
número de utente.
5. Género

Os géneros definidos são exactamente:

M — Masculino
F — Feminino
O — Outro
5.1 Nominativo

Para:

Masculino;
Feminino;

o nominativo segue a regra definida pela aplicação.

Para:

Outro

o nominativo é introduzido manualmente.

Esta decisão está fechada.

6. Cartão de Cidadão / documento de identificação

Esta é uma regra já definida há bastante tempo.

Regra funcional

O número deve:

ser tratado como texto;
não ser tratado como número inteiro;
preservar zeros à esquerda;
ser apresentado com o número de algarismos definido;
quando necessário, ser completado automaticamente à esquerda com 0.

Exemplo conceptual:

123456

pode tornar-se:

00123456

consoante o comprimento definido para o documento.

Regra crítica

Nunca permitir que a conversão para um tipo numérico elimine zeros à esquerda.

⚠️ Ainda preciso de recuperar do código/modelo a largura exacta que tínhamos efectivamente implementado para o Cartão de Cidadão, em vez de voltar a inventar um número. Esta será verificada directamente na versão-base antes de qualquer novo pacote.

7. Número de Utente

Foi explicitamente definido:

CHAR(9)

O número de utente:

tem sempre 9 algarismos;
deve ser armazenado como texto;
não deve perder zeros iniciais.
8. Datas

Esta é uma decisão transversal a toda a aplicação.

8.1 Apresentação e introdução

Para o utilizador:

dd/mm/aaaa

Formato europeu.

Aplica-se, nomeadamente, a:

Data de Nascimento;
Data de Inscrição;
Data de Eventos;
restantes datas apresentadas nos formulários.
8.2 Armazenamento na base de dados

Na base de dados:

aaaa-mm-dd

ou seja:

YYYY-MM-DD

A aplicação é responsável pela conversão entre:

dd/mm/aaaa

e:

YYYY-MM-DD
8.3 Máscara de introdução

A introdução deve permitir que o utilizador escreva apenas os algarismos.

Exemplo:

01011969

deve ser apresentado automaticamente como:

01/01/1969

As barras devem ser inseridas automaticamente.

8.4 Datas futuras
Data de nascimento

Não pode ser futura.

Data de inscrição
deve ser sugerida a data actual;
pode ser alterada para uma data anterior;
não pode ser posterior à data actual.
Eventos
deve ser sugerida a data actual;
pode ser alterada para uma data anterior;
não pode ser posterior à data actual.
9. Eventos

Os eventos constituem uma parte fundamental do histórico do associado.

9.1 Regra de preservação

Os eventos nunca são eliminados.

Devem ser mantidos mesmo que o associado:

seja desactivado;
seja posteriormente reactivado.
9.2 Eventos e estado do associado

Foi estabelecido que:

A desactivação de um associado é, em si mesma, consequência de um evento.

Portanto, o histórico de eventos deve permitir compreender a evolução da situação do associado.

9.3 Evento de Admissão

A inscrição de um novo associado gera automaticamente um evento:

Admissão

A data do evento:

deve corresponder à data de inscrição seleccionada;
não deve ser simplesmente assumida como a data/hora do sistema.
9.4 Tipos de evento

Existe uma tabela de:

tipos_evento

Os tipos são geridos através do backoffice.

Na criação inicial da base de dados, ficou definido que deve existir pelo menos:

Admissão
10. Inactivação e reactivação de associados
10.1 Inactivação

Um associado pode ser inactivado.

Essa operação:

não elimina o associado;
não elimina os seus eventos;
preserva o histórico.
10.2 Reactivação

Um associado inactivo pode ser reactivado.

A reactivação:

deve restaurar o associado ao estado activo;
não deve apagar o histórico anterior;
não deve obrigar automaticamente à associação a uma companhia.

Ficou explicitamente decidido que:

após a reactivação, será possível associar ou não o associado a uma companhia, conforme necessário.

11. Moradas

As moradas são uma entidade independente.

Existe uma tabela própria:

moradas

e tabelas de ligação.

11.1 Moradas partilhadas

Uma morada pode ser partilhada.

Isto é especialmente relevante para associados.

Exemplo:

Família
 ├── Associado A
 ├── Associado B
 └── Associado C
          │
          └── mesma morada
11.2 Correcção de uma morada existente

Se houver um erro, por exemplo:

Av. Marcos Portugal, Nº 53

quando deveria ser:

Av. Marcos Portugal, Nº 53A

deve ser possível corrigir a morada existente.

Essa alteração afecta todos os que partilham essa morada.

11.3 Substituição de morada

Também deve ser possível:

criar uma nova morada;
substituir a ligação à morada anterior.

Esta opção é diferente de corrigir a morada.

11.4 Histórico de moradas

Existe interesse em manter o histórico, especialmente para:

companhias;
Chefia Nacional;
associados.

As ligações devem permitir determinar períodos de vigência.

Conceptualmente:

DataInicio
DataFim

A morada actual é a ligação activa.

11.5 Chefia Nacional

A Chefia Nacional também pode mudar de morada.

Portanto, não pode existir qualquer tratamento especial que impeça a gestão histórica da sua morada.

12. Companhias

As companhias podem:

ser criadas;
ter uma morada inicial provisória;
mudar posteriormente de morada.

Embora seja pouco frequente, uma morada de companhia pode ser partilhada com:

outra companhia;
um associado.

O modelo deve suportar essa possibilidade.

13. Secções

Os associados podem estar relacionados com secções.

associados_seccoes

quando o modelo definido utiliza:

associados_secoes

A nomenclatura da base de dados e do código deve ser única e consistente.

14. Encarregados de Educação

Foi decidido que o encarregado de educação é uma entidade própria.

14.1 Não deve conter

Não existe necessidade de guardar, especificamente nesta entidade:

data de nascimento;
número de identificação;
tipo de documento;
NIF.
14.2 Deve relacionar-se com

Como já existem entidades próprias, o encarregado pode utilizar:

contactos;
moradas.
14.3 Relação com o associado

Um associado pode mudar de encarregado de educação.

Portanto, deve existir:

tabela de encarregados de educação
+
tabela de ligação

A relação deve permitir histórico.

15. Parentescos / tipos de relação

Foi criada a necessidade de uma tabela de relações/parentescos.

Deve suportar, entre outros:

Pai;
Mãe;
Avô;
Avó;
outros graus de parentesco;
Cônjuge.

O Cônjuge foi explicitamente acrescentado devido às necessidades dos contactos de emergência.

16. Contactos

Foi tomada a decisão de generalizar a tabela de contactos.

A gestão de contactos não deve ser duplicada desnecessariamente por diferentes entidades.

17. Contactos de emergência

Um associado pode ter:

1 ou mais contactos de emergência

A estrutura deve permitir:

nome;
contacto;
relação/parentesco.
17.1 Decisão estrutural

Foi discutida uma solução mais complexa baseada na ligação directa a entidades existentes.

Para já, foi aceite uma estrutura própria para contactos de emergência porque um contacto pode ser, por exemplo:

pai;
mãe;
amigo;
outra pessoa sem registo no SIGA.

Portanto:

Um contacto de emergência não pode obrigatoriamente depender da existência de outra pessoa registada no sistema.

18. Estados civis

Existe uma tabela de referência para:

estados_civis

Deve ser preenchida na criação inicial da base de dados.

19. Confissões religiosas

Existe uma tabela de referência para:

confissoes_religiosas

Deve ser criada e preenchida com os valores iniciais definidos.

20. Tipos de documento de identificação

Existe uma tabela de referência para:

21. Nacionalidades

Existe a tabela:

nacionalidades

O script de criação deve incluir a lista internacional de nacionalidades definida anteriormente.

A necessidade inicial era:

uma lista internacional de nacionalidades, não simplesmente uma lista de países.

24. Consentimentos

consentimentos

fichas_saude

26. Configuração

O ficheiro:

config/config.php

é o ficheiro de configuração que deve ser utilizado.

Esta regra foi explicitamente estabelecida depois de termos tido problemas repetidos com versões que:

não copiavam o ficheiro;
utilizavam outro config.php;
entregavam pacotes sem a configuração esperada.


27. Dirigentes e email associativo

Foi definido que:

Todos os dirigentes (associados enquadrados na secção "Chefia") possuem um
endereço de email associativo, para além do endereço de email pessoal.

27.1 Implementacao

Foi acrescentado o tipo de contacto "Email Associativo" a tipos_contacto,
distinto do tipo "Email" (pessoal) ja existente. Um associado pode ter
ambos os contactos em simultaneo, geridos na pagina de gestao de contactos.

⚠️ EM ABERTO: ainda por decidir explicitamente se o email associativo:
- e apenas mais um tipo de contacto disponivel (sem validacao), ou
- passa a ser obrigatorio para associados da seccao "Chefia", com validacao
  nessa mudanca de seccao, ou
- deve ser gerado automaticamente pela aplicacao a partir do nome (e com
  que formato/dominio).
Enquanto nao for decidido, a aplicacao apenas disponibiliza o novo tipo de
contacto, sem qualquer validacao ou geracao automatica.

27.2 Decisao (fechada)

Ficou decidido: o email associativo e OBRIGATORIO para associados na
seccao "Chefia", com validacao. Nao e gerado automaticamente.

Aplicado em:
- Registo de um novo associado directamente na seccao "Chefia": o campo
  fica obrigatorio no formulario e a submissao e bloqueada sem ele.
- Mudanca de seccao para "Chefia" a partir da edicao de um associado
  existente: exige que ja exista um contacto "Email Associativo" (gerido
  em "Gerir contactos"); caso contrario a mudanca de seccao e bloqueada.
- Remocao de contactos: nao e possivel remover o "Email Associativo"
  enquanto o associado estiver na seccao "Chefia".

Nao ficou coberto (fica para decisao futura, caso necessario): associados
que ja estivessem na seccao "Chefia" antes desta regra e que nao tenham
ainda um "Email Associativo" registado nao sao bloqueados retroactivamente
— nao ha, para ja, um relatorio que liste essas excepcoes.
28. Progressao entre seccoes

Foi corrigida a regra 28 (versao anterior estava incompleta): em uso
normal, a mudanca de seccao de um associado segue sempre a mesma ordem,
mas NAO tem de ser o passo imediatamente a seguir - pode saltar seccoes.
Nunca pode, em uso normal, recuar.

Sequencia (ordem, nao passo obrigatorio):
Colonia -> Alcateia -> Tribo Junior -> Tribo Senior -> Cla -> Chefia

Exemplo dado explicitamente: um lobito (Alcateia) que se afasta pode
voltar directamente como Senior (Tribo Senior) ou Caminheiro (Cla); um
Senior que se afasta pode voltar directamente como Chefe (Chefia).

28.1 Aplicacao

A regra aplica-se apenas a MUDANCAS de seccao de um associado ja
existente (ecra de edicao). NAO se aplica ao registo inicial de um novo
associado: a primeira seccao atribuida (na criacao) pode ser qualquer
uma - por exemplo, um dirigente adulto pode entrar directamente na
seccao "Chefia" sem alguma vez ter passado pelas seccoes mais novas.
Isto foi assumido por analogia com a forma como a regra foi comunicada
("mudancas de seccao"), e deve ser confirmado explicitamente se nao for
a leitura correcta.

Seccoes fora desta sequencia (caso venham a ser criadas no futuro via
administracao) nao ficam sujeitas a esta regra.

28.2 Correccao de erros

Foi explicitamente pedido que seja possivel corrigir um erro (ex.:
atribuicao a seccao errada por lapso), o que pode implicar um recuo na
sequencia. Isso e feito atraves de uma opcao explicita no formulario de
edicao ("Isto e uma correccao"), que:
- ignora a regra de progressao normal (permite recuar);
- fica sempre registada no historico de eventos do associado, com o tipo
  de evento "Correccao de seccao" e, quando indicado, o motivo escrito
  pelo utilizador;
- nao dispensa a regra do email associativo obrigatorio (27) quando o
  destino da correccao for a seccao "Chefia".

29. Pertenca simultanea: companhia local, Chefia Nacional e orgaos

Foi definido que um dirigente pode estar simultaneamente em varias destas
combinacoes:
- numa companhia local e na Chefia Nacional;
- numa companhia local e num ou mais orgaos (tabela nova: orgaos);
- apenas num ou mais orgaos, sem qualquer companhia.

29.1 Chefia Nacional

Confirmado explicitamente: a "Chefia Nacional" e a companhia ja existente
nos dados iniciais (ambito_global = 1) - nao e um conceito novo. Mas
passou a ser gerida de forma independente da companhia local, porque as
duas podem coexistir (ao contrario do que a logica anterior assumia, que
so permitia uma companhia activa de cada vez).

29.2 Orgaos (tabela nova)

Criada a tabela `orgaos` (Id, Designacao, Activo) e a tabela de ligacao
`associados_orgaos` (com DataInicio/DataFim/Activo, como as restantes
ligacoes historicas). Confirmado explicitamente: um dirigente pode estar
em varios orgaos em simultaneo - por isso a ligacao permite multiplas
linhas activas para o mesmo associado.

⚠️ EM ABERTO: a lista de orgaos ainda nao foi indicada. A tabela fica
vazia no script de instalacao (sem dados inventados) ate essa lista ser
fornecida.

29.3 Aplicacao

- A companhia local mantem a logica de exclusividade (uma de cada vez).
- A Chefia Nacional e gerida por uma opcao propria ("Pertence a Chefia
  Nacional"), independente da companhia local.
- Os orgaos sao geridos por seleccao multipla, independente de tudo o
  resto.
- Isto esta disponivel tanto no registo inicial como na edicao do
  associado.

⚠️ EM ABERTO: nao ficou explicitamente decidido se a pertenca a Chefia
Nacional e a orgaos deve ficar reservada apenas a associados na seccao
"Chefia" (dirigentes) ou se pode ser atribuida a qualquer associado. Por
enquanto a aplicacao NAO impede que sejam atribuidos a um associado fora
da seccao "Chefia".
